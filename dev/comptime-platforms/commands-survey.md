# Command architecture survey

## Current observations

- **Contract and dispatch.** `src/api.zig` defines `Ctx` and `Command`: stdin/document to stdout/document, diagnostics on stderr and optional person-facing `tty`. `src/command.zig` is the registry; its module tuple drives command lookup and split `m8-CMD` builds. `src/main.zig` handles overview, launcher shorthand (`@`/address to `at`), self-path and dispatch; `src/harness.zig` builds the context, reads the input and runs/report errors for a command. `src/launch.zig` resolves sibling executables and runs commands as programs (`under`/`become`).
- **Direct in-process orchestration.** `at` (`command/at.zig`) is expressly the one-process pipeline: it assembles the address, calls `converse.run`, and tags/follows the result; `main` routes shorthand there. `query.zig` and `ref.zig` also assemble a conversation/request directly (imports overlap `at`: address, assembly, converse, ledger); `send.zig` calls `converse`, while `reset`, `tag`, `top`, `tail`, `exclude`, `render`, `parse`, `encode`, `register`, and `models` mostly operate directly on context/config/document/provider primitives. These are command modules, not shell pipelines.
- **Conversation core.** `src/converse.zig` orchestrates `agent`, `policy`, `provider`, `session`, `ledger`, `toolbox`, and `shield`; it imports `command/call.zig` for tool execution. Thus chat/tool turns stay inside the Zig process until an external command is needed. `send` is a narrower entry into the same conversation machinery; `at` owns the interactive assembly/follow-along flow.
- **Spawn and pipeline boundary.** `call.zig` expands argument lines (`call/argline.zig`) then spawns a process, inheriting stdin and capturing stdout/stderr to frame records/markdown/status. `--no-wrap` accepts records the child emitted; definitions may select this behavior. `launch.zig` can invoke sibling command binaries, and `riff.zig` uses `provider.selfPath` and process launching for its external interactive/TUI path. `munge.zig` dispatches read/write/scan/regex work to its submodule runners (and has command lookup); distinguish that subcommand dispatch from a process pipeline. `watch.zig` is a stateful ledger/session watcher, not the conversation loop.
- **Tool, shield, provider execution.** A tool definition is resolved by `agent`/`toolbox`; `converse` applies policy and shields around tool calls, with `call.execute` at the process boundary. `secure-shield.zig` uses `sandbox`; `ask-shield.zig` and `shield/wrapping.zig` supply ask/wrapper behavior. `url-provider.zig` implements the HTTP-facing provider command, selecting curl or Zig's HTTP client at comptime; even its stdlib transport resolves configured header values through shell commands. `toy-provider.zig` is an in-process mock provider (including Eliza/Z-machine components). `models.zig` queries provider model info. `provider.zig` resolves provider entries and their configured `cmd`, `encode`, `parse`, `models` command names; `main` documents these as `M8_PROVIDER_*` environment configuration. `call` supplies tool execution/framing, but it is not a universal process gateway: `provider.run` spawns its own encode/cmd/parse pipeline; launcher, HTTP/header handling, shield wrappers, and riff also have distinct launch paths.
- **Document/ledger utility families.** `at`, `query`, `ref`, `send` concern turns and address assembly; `tag`, `tail`, `exclude`, `top`, `reset`, `watch` inspect or mutate conversation/session history; `parse`, `render`, `encode` translate/render documents and protocol payloads; `register` changes config; `munge` groups document transformations. `riff` is the large interactive workflow and is less like a small stream filter than the rest. `call`, `secure-shield`, `ask-shield`, `url-provider`, `toy-provider`, `models` are execution/provider infrastructure exposed in the same registry.
- **Definition scripts / core.** `config.zig` documents discovery of nearest-first `core/` directories and separates authored `@` definitions from generated state. Provider configuration is `core/providers.json` per `main.zig` help and `docs/providers.md`; definitions can name tools, shields and providers consumed by `agent`/`converse`/`toolbox`. The checked-in tree has `src/core/mac-sandbox.sb` (sandbox policy), but no obvious checked-in `core/` directory of command-definition scripts. Treat definition scripts as configuration inputs, not additional Zig commands; confirm what is shipped/installed by build/package before asserting a canonical set.

## Questions for the comptime/platform plan

- Which commands need to remain in every launcher versus split binaries? The registry/build option is the central boundary, but `at`/`converse` and indirect `call`/provider resolution may impose transitive inclusion or executable-path requirements.
- Should `munge` subcommands and `riff`/watch modes be modeled as command graph edges, process launches, or both? Verify the actual spawn sites before flattening orchestration into a single graph.
- Which platform-facing behaviors should be isolated: `call` process I/O, sibling lookup in `launch`, HTTP in `url-provider`, sandbox/shield wrappers, terminal handling in `api`/`harness`/`riff`/`watch`?
- Where are core definitions installed or supplied in deployments, and which command names do they invoke? The source tree alone does not establish a shipped definition-script inventory.
