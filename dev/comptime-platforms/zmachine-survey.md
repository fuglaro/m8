# Z-machine runtime and platform survey

Scope: selective source survey for planning. This records current behavior and feasibility boundaries; it does not prescribe a design.

## Observations

- **The interpreter core is separated from m8 and host I/O.** `src/zmachine/` contains story parsing, Z-string/ZSCII handling, objects, dictionary/tokenization, screen streams, keys, and opcode execution (`story.zig`, `text.zig`, `object.zig`, `dict.zig`, `screen.zig`, `keys.zig`, `machine.zig`). `Machine.create` takes story bytes and a seed; execution mutates in-memory story/machine/screen/stack state and stops at input or quit. No file, process, clock, network, or terminal calls appear in the core. `zmachine.zig:155-204` exposes `play(arena, bytes, seed, inputs)` and returns text, stop/ended state, and consumed-input count.
- **Input/output are explicit boundaries.** The interpreter yields at line or character input (`machine.zig:48-56, 848-880`); `play` supplies lines or key presses from its input slice, resumes execution, and collects emitted screen text (`zmachine.zig:155-226`). There is no interactive terminal input loop. Screen behavior is an in-memory headless profile (80 columns, no color/sound/timed input), with output streams/windows folded into text (`story.zig`, `screen.zig`; `src/zmachine/README.md:112-119`).
- **Time and randomness do not use host sources.** `Rng` is deterministic SplitMix64; `random 0` reseeds from the original seed and a counter, not a clock (`machine.zig:87-139`). V1–3 status text uses game globals for score/moves or game time; this is not wall-clock time (`zmachine.zig:226-273`). Same story, seed, and inputs replay deterministically; seed derivation hashes the first message (`zmachine.zig:131-148`).
- **Persistence opcodes are emulated, not backed by host storage.** Save/restore/undo (including table forms) follow version-specific failure behavior; restart reinitializes deterministically. No save-file/Quetzal implementation or filesystem persistence exists in the machine (`machine.zig:19-29, 790-831`; `src/zmachine/README.md:38-43, 190-195`).
- **Process/file effects sit in drivers.** `src/zmachine/cli.zig:14-69` reads a story path and writes stdout, using Zig process/IO APIs; `build.zig:78-95` makes `zrun` a separate executable. The m8 adapter `src/command/toy-provider/zmachine.zig:81-119, 185-258` discovers config directories, reads story files (16 MiB bound), unwraps Blorb `ZCOD`, and maps provider records to `play`; it emits m8 records and diagnostics. Story names are constrained beneath `core/Z-Machine`; extensions and exact-case matching are implemented there (`:31-119`).
- **Actual m8 integration is model/provider integration, not a Z-machine tool.** The adapter serves `/toy/Z-Machine/<story>` and replays user records; it ignores prior assistant records (`src/command/toy-provider.zig:96-105`; `src/command/toy-provider/zmachine.zig:185-258`). It does not expose opcodes or a persistent live machine to tools. The separate CLI is a developer runner, not a shipped browser interface.
- **Sandboxing is an outer process concern.** `src/sandbox.zig` resolves and invokes macOS `sandbox-exec` profiles (`:1-20, 117-166`); this is not a sandbox around VM story execution. Other restrictions include filesystem/process/network policy for descendants, but the mechanism is specifically macOS. No Z-machine-specific sandbox or browser security layer is present.
- **Comptime/platform boundary visible today.** Story version selects behavior at runtime per loaded story; session state (PC, stack, RNG, pending input, screen) is also runtime data (`machine.zig:143-180`). Build target and optimization are selected through standard Zig build options (`build.zig:4-7`); interpreter semantic provenance is computed at compile time by hashing source (`zmachine.zig:44-74`). The instruction set/version and story-dependent profiles are not build-target selection. No explicit Wasm/browser target, JS bridge, browser storage, or browser UI is implemented in these files.

## Browser/Wasm feasibility boundary

The byte-oriented interpreter API has a plausible portable boundary: story bytes, seed, and supplied inputs in; allocated output and execution status out. Its implementation uses Zig standard-library memory/container/hash/format facilities rather than OS services. A caller would still need to provide story bytes and input events and display output. The existing CLI and m8 adapter depend on filesystem, process/environment/config discovery and terminal/record I/O, so they are not themselves browser hosts. This is an observation of source dependencies, not a claim that a Wasm build has been verified; no tests or target builds were run for this survey.
